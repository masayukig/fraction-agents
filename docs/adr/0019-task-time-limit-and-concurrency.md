# 0019. 汎用ホストに、1 回の依頼の時間の上限と、係全体の同時実行の上限を足す

- Date: 2026-10-15
- Status: Accepted

## Context

長い調べもの（ADR 0022 の deep research の係）を汎用ホスト（ADR 0007）の上に作る。1 回の依頼が数十分かかり、その間ずっと ChatGPT Plus の枠を使う。

今の汎用ホストには、次の 2 つの上限が無い。

- 1 回の依頼の時間の上限。`idleTimeoutSeconds` は使われていない context の pi を止める時間であり、`inputTimeoutSeconds` は聞き返しの答えを待つ時間である。
  走っている依頼は、モデルが終えるか、呼び出し元が CancelTask で止めるまで続く。止まらない依頼は Plus の枠を食い続ける。
- 係全体で同時に走る依頼の数の上限。並ぶのは context ごとに 1 つまで（走っている context に次の依頼を送ると `REJECTED`）だが、context が違えばいくつでも並んで走る。
  Plus の枠はアカウント単位で、本人・なつみ・ほかの係と分け合っている（ADR 0002）。長い依頼がいくつも並ぶと、ほかが枠に当たる。

本人と決めたこと（deep research の係の設計）は次のとおりである。

- 時間の上限を設け、既定は 60 分程度で、設定で変えられる。依頼の文で短くできる。上限に来たら、そこまでの結果を「途中まで」と明記して返し、失敗にしない。続きは同じ context で「続けて」と頼む。
- 係全体で同時に走るのは 1〜2 件までで、設定で決める。超えた依頼は断らずに `submitted` のまま順番を待たせる。呼び出し元は `task get --wait` で待つだけでよい。

どちらも係の中身に依らない仕組みなので、汎用ホストの機能にする。

## Decision

### 時間の上限

- 汎用ホストの設定に `taskTimeLimitSeconds` を足す。既定は無し（上限なし）で、今の係の振る舞いは変わらない。
- 数えるのは、依頼が走っている（`working`）時間だけである。順番を待つ時間と、聞き返しの答えを待つ（`input-required`）時間は数えない。
- 上限に来たら、ホストは止める前に、走っている pi に「時間の上限に来た。ここまでの結果で返事を出して終える」ことを告げる（Pi の RPC で、走っている prompt に割り込むメッセージを送る）。
  告げた文は決まった文で、ホストが持つ。
- 告げてから猶予（既定 5 分、`taskTimeLimitGraceSeconds`）のうちに終われば、その結果で `completed` にする。
- 猶予を過ぎても終わらなければ、ホストは prompt を止める（CancelTask と同じ止め方）。そのうえで `completed` にする。`canceled` や `failed` にはしない。
  - 返事の取り決め（ADR 0015）の返事がそれまでに出ていれば、その返事を返す。
  - 返事が出ていなければ、時間の上限で止めたこと、同じ context で「続けて」と頼めば続きから調べられることを書いた決まった文を返す。
- どちらの終わり方でも、上限に来た依頼の状態のメッセージに、時間の上限で途中までを返したことを書く。返事の中身（`summary` など）はホストが書き換えない。
- セッションのファイルは残るので、同じ context の次の依頼は、途中までの経過を覚えたまま続く（ADR 0002）。
- 依頼の文で短くするのは、モデルの側で行う。ホストが依頼の文を読んで上限を変えることはしない。ホストが守るのは設定の上限だけである。
  モデルが経過した時間を知る手段（道具か、prompt に添える時刻か）は実装で決める。
- 退けた案: 上限に来たらすぐ止めて `failed` にする。数十分の調べものが何も返らない。
- 退けた案: 上限を設けず、止めるのは呼び出し元の CancelTask に任せる。呼び出し元が忘れれば止まらない。

### 係全体の同時実行の上限

- 汎用ホストの設定に `maxConcurrentTasks` を足す。既定は無し（上限なし）で、今の係の振る舞いは変わらない。
- 上限に達しているときに来た依頼は、断らずに `submitted` のまま待たせ、来た順に走らせる。
  - 呼び出し元から見ると、依頼はすぐに受け付けられ、`submitted` のまま時間がかかるだけである。`task get --wait` で待てる。
  - 待っている依頼も、その context を塞ぐ。同じ context に次の依頼を送ると、今と同じく `REJECTED` になる。
  - 待っている依頼を CancelTask で止めると、走らせずに `canceled` にして列から外す。
- 聞き返しの答えを待っている依頼は、枠を手放す。答えを待つのは最長で `inputTimeoutSeconds`（既定 1 日）であり、その間ほかの依頼を止めないためである。
  - 答えが届いたら、その依頼は `submitted` に戻って枠を待つ。新しい依頼より先に走らせる。始めた依頼を先に終わらせるためである。
  - 答えは届いた時点で受け付け、枠が空いたときに pi に渡す。
- 待っている列は持続しない。ホストを再起動したら、走っていた依頼と同じく、待っていた依頼も `failed` にする（今の「再起動の時点で走っていた Task は `FAILED`」に揃える）。
- 退けた案: 上限を超えたら `REJECTED` で断り、呼び出し元に送り直させる。呼び出し元ごとに送り直しの処理が要り、なつみの郵便ポストのような自動の依頼が取りこぼす。

### 実装で決めたこと

- 上限を告げるのは Pi の RPC の `steer` である。今の turn の道具の実行が終わり、次にモデルを呼ぶ前に届く。告げられなかった（pi がまだ起動していないなど）ときも、猶予は数え始める。
- モデルが経過した時間を知る手段は、prompt に添える時刻にした。上限があるときだけ、ホストは依頼の文の末尾に、上限の長さと数え始めた時刻を書いた決まった注記を足す。モデルは `date` で今の時刻を見る。道具を足すより変わる所が少なく、上限の無い係の prompt は変わらない。
- 猶予も、答えを待つ間は数えない。
- ホストを止める間は、待っている依頼に枠を渡さず、記録も変えない。次の起動で、走っていた依頼と同じく `failed` になる。

## Consequences

- 長い依頼を受ける係が、設定だけで Plus の枠と Pod の資源の使い方を抑えられる。今の係は設定を書かなければ何も変わらない。
- 上限に来た依頼が `completed` になるので、呼び出し元は状態だけでは「全部終えた」と「途中まで」を見分けられない。状態のメッセージと返事の文で見分ける。
- 上限の直前に告げてもモデルがまとめきれない場合がある。途中で返事を出し直す（`submit_reply` は後の返事で置き換わる）ように係の指示に書けば、止めたときに残る返事が増える。
- 待たせた依頼は、前の依頼が終わるまで何十分も `submitted` のままになりうる。呼び出し元が待ちの上限を短くしていれば、そちらで先に諦める。
- 待っている列はメモリにしか無いので、再起動で失われ、待っていた依頼は失敗になる。呼び出し元は送り直す。
- 聞き返しに答えた後でも、ほかの依頼が枠を使っていれば、すぐには続かない。
