# 0017. ニュース係: 情報源を定期的に取り込んで貯め、依頼の関心に沿って一次選別して返す

- Date: 2026-10-11
- Status: Accepted

## Context

秘書のなつみが、本人の関心に合いそうなニュースを、本人に頼まれなくても定期的に受け取り、会話の機会に話題にしたい。

なつみの側では、サーバーが cron で、モデルのターンを経ずに A2A の依頼を送る仕組み（以下、郵便ポスト）を作る。
定期便は、なつみの記憶に 1 通 1 ファイルで投函し、相手・cron・依頼の本文を書く。返事は、なつみが頼んだときの返事と同じく
`/sources` にファイルで置かれ、`sources_updated` で知らされる（natsumi の ADR 0069）。郵便ポストそのものは natsumi の ADR で決める。
郵便ポストは汎用で、ニュースのほか、Gmail Agent（ADR 0016）やカレンダー係（ADR 0014）への定期の依頼にも使う。

ニュースを集めて選ぶ役をどこに置くかについて、次のことが分かっている。

- なつみ本体にフィードの取得とページの読み取りを足すと、なつみの Pod の外への出口が広がる。
  記事の本文が、なつみの 1 日のセッションの文脈に入る。記事は外の誰でも書ける文であり、仕込まれた指示がなつみの権限に届く。
- フィードの取得は決まった手順で、LLM は要らない。関心に合うかの選別は、LLM が要る。
- 情報源には、入れ替わりの速いもの（数時間で古い記事が一覧から消えるもの）がある。依頼のときにだけ取りに行くと、その間に消えた記事を取りこぼす。
- フィードの公開時刻は、情報源によって欠けていたり、後から古い時刻の記事が足されたりする。
- 汎用ホスト（ADR 0002・0007）の pi のプロセスは context ごとに立ち、使われなくなると止まる。
- 調べもの係（ADR 0013）の Pod の外への出口は、NetworkPolicy を強制できる CNI に移るまで絞っていない。
- 返事の取り決め（ADR 0015）の `sections` と `sources` は、空でよい。

そこで、Gmail Agent と同じ責任の分け方で、fraction-agents にニュース専用の係（以下、ニュース係）を立て、なつみは A2A で頼む（ADR 0001）。
定期の依頼に共通する「前回からの新着」の基準も、ここで全係の取り決めとして決める。

## Decision

### 係の役割

ニュース係となつみの責任を次のように分ける。

| 責任 | 持ち手 |
|---|---|
| 関心の方針の正本と、依頼を送ること | なつみ（定期便の本文） |
| 情報源の取得と、取り込んだ記事の保存 | ニュース係 |
| 依頼に添えられた関心の方針に沿った一次選別 | ニュース係 |
| 何を本人に話すかの最終判断 | なつみ |
| 情報源の一覧の変更 | 本人（PR） |

- ニュース係は、依頼の本文に書かれた関心の方針に沿って新着の記事から候補を選び、候補ごとに要約・選んだ理由・URL を返す。
- ニュース係は、関心の方針を自分の正本として持たない。方針は依頼ごとに本文で受け取る。
- 記事の本文に触れるのは、ニュース係のモデルだけとする。なつみには、選んだ候補の要約だけが返る。
- 記事の本文と概要は外部のデータとして扱い、命令として実行しない、と係の AGENTS.md に書く。
- モデルは、ほかの係と同じ ChatGPT Plus の経路（`openai-codex`）を使う。
- 取得はスクリプト（係のコード）で行い、選別は LLM で行う。

### 収集

- ニュース係は、依頼とは別に、係のプロセスの中のタイマーで定期的に全情報源を取り込む。
  依頼のときにだけ取りに行く形にはしない。入れ替わりの速い情報源でも、依頼の間に一覧から消えた記事を取りこぼさないためである。
  - pi のプロセスは context ごとに立って止まるので、タイマーはそこには置けない。係の Pod の中のどのプロセスでどう動かすかは、実装で決める。
- 取り込んだ記事は、係の PVC の上のストアに貯める。記事ごとに、正規化した URL・題・概要・情報源・公開時刻・取り込んだ時刻を持つ。
- 記事は正規化した URL で重複を除く。同じ記事を次の取り込みでまた見ても、新しい記事にしない。
- 記事は、取り込んでから 30 日で消す。
- 「新着」の基準は、公開時刻ではなく **取り込んだ時刻** とする。
  - 公開時刻が欠けている記事や、後から古い公開時刻で足された記事も、取り込んだ時点で新着になり、落ちない。
  - 公開時刻は、候補の本文に添える情報として持つ。
- ストアは、次の性質を満たす。
  - 取りこぼさない。取り込みの失敗や途中の停止で、まだ渡していない記事を失わない。
  - 重複しない。同じ記事を 2 つの記事として持たない。
  - 再起動で壊れない。書き込みの途中で止まっても、次に起動したときに読める。取り込みと、依頼を処理する道具が同時に触れても、書きかけを読まない。

### 情報源

- 情報源は、係の設定 `news.json` に `{name, kind, url}` の並びで書く。`news.json` は環境固有なので、private の overlay に置く（ADR 0010）。
  このリポジトリには、架空の情報源を書いた例だけを置く。
- 情報源を変えるのは本人で、overlay の PR で行う。取得先は係の外への出口なので、変更は本人の目を通す。
  - なつみは、情報源の追加を会話で本人に提案するだけで、`news.json` を変えない。
- 初版の `kind` は `feed`（RSS と Atom の汎用の取得）だけとする。
  - 専用の取り方が要る情報源（フィードの無い一覧のページなど）は、要るときに `kind` を足す。そのコードは Pi パッケージの `pi-package/lib/` に置く。
- 記事の本文は、取り込みの段階では取らない。フィードの概要で選別に足りない記事だけ、選別のときに係のモデルが道具で読む。
  道具は、調べもの係（ADR 0013）の取得の道具と同じものを想定する。

### 「前回の受け取り」の行（全係の取り決め）

郵便ポストは、定期便ごとに前回うまく返事を受け取った時刻を覚え、次の依頼に添える。係はこの時刻で「前回からの新着」を決める。
これはニュース係に限らず、定期便の相手になる全係の取り決めとする。

- 依頼の本文の末尾に「前回の受け取り: <時刻> (JST)」の 1 行がある。A2A の message の metadata にも同じ値が載る。
- 係は、この行があれば、その時刻より後を新着の基準にする。
- 行が無ければ（郵便ポストの初回、定期便を作り直したとき、人やなつみがその場で頼んだとき）、係の既定の範囲を使う。ニュース係の既定は直近 24 時間とする。
- 本文の言い回し（「今日の」「重要なものだけ」など）と行が食い違うときに、どちらに従うかは係が判断する。
- 係は、前回どこまで返したかを覚えない。基準を持つのは郵便ポストである。郵便ポストは失敗した回の時刻を進めないので、失敗した回の分は次の依頼に含まれる。
- ニュース係・Gmail Agent・カレンダー係を含む全係の Agent Card の説明と AGENTS.md に、この行の扱いを書く。書き換えは、それぞれの実装の PR で行う。
  - 汎用ホストは、いまは message の metadata を pi に渡さない。係のモデルが読むのは本文の行である。
- 郵便ポストが記録する時刻は、境目で記事を落とさないために、係が前回の依頼を処理し始めた時点より後であってはならない。
  どの時点の時刻を記録するか、時刻の書式と metadata の名前は、郵便ポスト（natsumi の ADR）で決める。

### 返事

- 返事は、返事の取り決め（ADR 0015）の `submit_reply` で返す。
- 候補 1 件を 1 節とする。
  - 節の題は記事の題、本文は要約・選んだ理由・情報源・公開日とする。
  - `sources` に候補の記事の URL を入れる。
- `summary` に「新着 N 件中 M 件を選んだ」ことと、主な話題を書く。
- 候補は、既定で最大 10 件とする。依頼の本文で「5 件まで」のように変えられる。
- 任意の節「情報源の提案」を置ける。候補を選ぶうちに、一覧に無いがよく出てくる情報源に気づいたときに書く。
- 新着の記事が無いときは、`sections` を空にして返す。
  - 返事の取り決めでは、`sections` が空の返事を「中身なし」とみなす。郵便ポストはこれを本人に知らせず、`/sources` にも置かない。
  - 取り決めの形は変わらないので、版は v1 のままとする。

### 実装で決める事項

次の事項は、この ADR では決めない。後続の実装で決め、必要なら ADR に追記する。上の「ストアは、次の性質を満たす」は、どの形でも守る。

- ストアの形（ファイルか SQLite か）と、URL の正規化の規則。
- 取り込みの間隔の既定値（1 時間ごとを目安とする）、取り込みのタイマーをどのプロセスで動かすか。
- 取得の失敗と再試行（回数・間隔、失敗が続く情報源の扱いと、それを誰にどう見せるか）。
- フィードの大きさ・1 回に取り込む記事の数・概要の長さの上限。
- 選別のときに本文を読む道具の具体と、pi の組み込みの道具を出すか（調べもの係・カレンダー係・Gmail Agent は出していない）。
- 係の名前、`news.json` の細かい形（`kind` ごとの項目）、係の道具の形。
- 新着の記事はあったが選んだ候補が無いときに、`sections` を空にする（中身なし）か、件数だけを知らせるか。
- 期間を扱わない係（Wiki 管理人・調べもの係など）の AGENTS.md に、「前回の受け取り」の行をどう扱うと書くか。

## Consequences

- なつみの Pod の出口と、なつみの 1 日のセッションの文脈は広がらない。記事の本文と仕込まれうる指示は、ニュース係の中で閉じる。
- 一次選別の質は係のモデルに、最終判断はなつみにある。係が選ばなかった記事は、なつみにも本人にも届かない。
- 係は依頼のあいだで何も覚えないので、同じ記事でも、基準の時刻の重なる依頼（行の無い依頼など）にはまた返すことがある。
  何を本人に話したかを覚えるのは、なつみである。
- 一度取り込んだ記事は、情報源の一覧に残り続けても新着にならない。ただし 30 日を過ぎて消した記事が一覧にまだ残っていれば、もう一度取り込まれて新着になる。
- 前回の受け取りが 30 日より前のときは、残っている 30 日分だけが対象になる。
- 取り込みは依頼が無くても動くので、係は情報源へ定期的に出ていく。依頼の無い時期にも、ストアと外への通信が続く。
- 選別のときに係のモデルが記事の本文を読むので、取り込みの情報源の一覧の外にあるページへも出ていく。
  出口は調べもの係と同じく当面絞らないので、ADR 0013 の「出口は当面絞らない」の危険を同じく抱える。
- 全係の Agent Card と AGENTS.md に「前回の受け取り」の行の扱いを書く変更が、各係の実装の PR に要る。
- 「中身なし」の意味は返事の取り決めの上に重ねたもので、`sections` が空の返事を出す係は、郵便ポストからの依頼ではその回が知らされないことを前提にする。
  文章だけを返す相手は空を表せないので、郵便ポストからは毎回知らされる。

## 実装での決定（2026-10-11）

「実装で決める事項」を、実装で次のように決めた。細部と運用は `agents/news-agent/README.md` にある。汎用ホストは変えていない。

### 係の作り

- 係の名前は `news-agent`。汎用ホストの上に作り、道具は Pi パッケージの拡張 `news` に足した。
- 道具は、取り込んだ時刻で記事を引く `news_articles` と、情報源の状態を見る `news_sources` の 2 つで、どちらもストアを読むだけである。
- 本文を読む道具は、調べもの係と同じ `@kvidzibo/pi-web-access` の `fetch_content`（と `get_search_content`）にした。
  外の検索サービスに出る `web_search` は、汎用ホストの設定で外し、拡張でも止める。pi の組み込みの道具は出さない（`defaultTools: []`）。
- image は、汎用ホストに `@kvidzibo/pi-web-access` だけを足した Dockerfile の target `news-agent`（`ghcr.io/yuanying/fraction-agents-news-agent`）にした。
  - 退けた案: 調べもの係の image を使う。使わない Chromium を抱えることになる。
  - 退けた案: 汎用ホストの image に足す。ほかの係の image が重くなる。

### 取り込みのタイマー

- タイマーは、係の Pod の中の別のコンテナ `collector` で動かす。同じ image で `pi-package/bin/news-collect.ts` を動かし、起動するとすぐに 1 回、その後は間隔ごとに全情報源を取り込む。
  ボリュームの `data/` をホストと共有し、ストアは `/data/news` に置く。
  - 依頼の有無にかかわらず動き、落ちれば kubelet が立て直す。ホストの再起動とも、pi の起動・停止とも関わらない。
  - 退けた案: 汎用ホストの中のタイマー。どの係でも使う汎用ホストに、ニュース係に固有の仕事が入る。
  - 退けた案: CronJob。ReadWriteOnce のボリュームを、別の Pod から使うことになる。
- 間隔の既定は 60 分で、`news.json` の `intervalMinutes`（5〜1440）で変えられる。

### ストア

- ストアはファイルで持つ。取り込んだ日（UTC）ごとの記事のファイルと、情報源の状態のファイルである。
- 書くのは収集係だけで、道具は読むだけである。書き込みは、いつも一時ファイルに書いて fsync し、rename で置き換える。
  読む側には古いファイルか新しいファイルのどちらかが見え、書きかけは見えない。書き込みの途中で止まっても、古いファイルが残る。
  収集係は、起動のたびに残った一時ファイルを消し、読めないファイルを脇に置く。
  - 退けた案: SQLite。別のコンテナの 2 つのプロセスで、同じデータベースのロックとジャーナルを共有することになる。書き手が 1 つなら、ファイルの置き換えで足りる。
- 収集係は、情報源ごとに、新しい記事を書き込んでから次の情報源に進む。止まっても、書き込んだ記事は失わず、残りの情報源は次の回に取り込む。
- 取り込んだ時刻は、その情報源の記事を書き込む直前の時刻とする。時刻を付けてから書き込みが読む側に見えるまでには、ミリ秒の幅のずれがある。
  道具が記事を引いた瞬間がこの幅に重なると、その記事は今回の依頼に入らず、次の依頼の基準の時刻より前にもなりうる。この幅は小さいので、ロックで防ぐことはしない。
- URL の正規化: 相対の URL はフィードの URL を基準に絶対にし、`http`・`https` だけを記事にする。断片・既定のポート・追跡のためのクエリ（`utm_*`・`fbclid` など）を外し、
  残りのクエリを名前で並べ、スキームとホストを小文字にする。パスは書かれたまま残す（ページを取り違えないため）。
- 30 日の削除は、各回の取り込みの後に行う。道具も、30 日より前に取り込んだ記事を出さない。

### 情報源と失敗

- `news.json` は `{timeZone, intervalMinutes, storeDir, sources: [{name, kind, url}]}` とした。`sources` だけが必須で、`kind` は `feed` だけを受ける。
  名前と URL の重複、知らない項目、`http`・`https` 以外の URL は断る。
- フィードは RSS 2.0・RSS 1.0（RDF）・Atom を読む。XML は依存の無い小さな読み手で読み、DOCTYPE で宣言された実体は展開しない。
- 上限: 1 回の取得は 30 秒、フィードは 5 MB、1 回に読む記事は 200 件、題は 300 文字、概要は 500 文字。
- 再試行は、応答が無い・429・5xx のときだけ、1 回の取り込みで 3 回まで（`Retry-After` に従うか、2 秒・8 秒の間を空ける）。ほかの 4xx は試し直さない。
  ETag と Last-Modified で条件付きに取得する。
- 情報源ごとに、続けて失敗した回数・最後の誤り・最後に取り込めた時刻を残す。`news_articles` の結果に全情報源の状態と、
  収集係が間隔の 2 倍より長く動いていないときの警告を出す。係は、3 回以上続けて失敗している情報源や停止を、返事に書く。

### 返事と「前回の受け取り」の行

- 新着の記事はあったが選んだ候補が無いときも、`sections` を空にする（中身なし）。要約に「新着 N 件中 0 件」と書き、失敗が続く情報源があれば要約に 1 行で書く。
- 候補があるときは、任意の節「情報源の提案」と「取り込めていない情報源」を候補の節の後に置ける。候補が無いときは置かない。
- 係のモデルは行の時刻を `news_articles` の `since` にそのまま渡し、道具が読む。オフセットの無い時刻は断る（推測しない）。
- 期間を扱わない係の扱い: 調べもの係・Wiki 管理人は「使わない。本文が前回から後のものを頼んだときだけ基準にする」と書いた。
  カレンダー係は、予定がいつ追加・変更されたかを道具で見分けられないので、期間は本文で決め、行は使わないと書いた。
  Gmail 係は、本文に期間が無ければ行の時刻より後に届いたメールを対象にする（`after:` は日付の区切りなので、前日から探して受信の時刻で絞る）。
